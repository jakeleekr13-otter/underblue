# Colour evaluation harness

This harness measures the colour algorithm on still images. It compiles the app's own Processing sources into a Mac command-line tool. So it measures the shipping code, not a copy.

## What it renders

For each image the tool renders these variants:

| Variant | Meaning |
|---|---|
| `original` | The source, no correction |
| `grayworld` | A simple gray-world white balance, as a floor to beat |
| `current` | `FilterEngine.apply` only (the fallback path) |
| `restoration` | The physical restoration only, blended by plan confidence |
| `combined` | `RestorationEngine.combined`, the shipping output for photo, batch and video |
| `uniform` | `combined` with one constant (median) depth. It stands in for the video path |
| `reference` | The target image, when the data set has one |

## Metrics

All metrics come from the rendered 8-bit sRGB image.

- **deltaE**: mean CIE76 colour difference to the reference. Lower is closer.
- **PSNR**: over RGB, against the reference.
- **SSIM**: on L*, 8x8 box windows, stride 4.
- **meanL**: mean L*. This is overall brightness.
- **localContrast**: mean L* standard deviation in 16x16 windows. A water veil lowers it, so it works as a haze measure that does not depend on hue.
- **farLocalContrast**: the same, but only in the far 30% of the depth map (mostly water).
- **farHue / farChroma**: the CIELAB hue angle and chroma of the far region's mean colour.
- **farHueOK / farChromaOK**: the same in OKLab.
- **nearRG**: the red / green ratio in the near 30% of the depth map (mostly the subject).
- **contrastL**: global L* standard deviation.

### Why OKLab for water hue

- CIELAB hue cannot tell blue colours apart. Azure is 273°, pure sRGB blue is 306° and violet is 310°.
- OKLab separates them. Cyan is 208°, azure 249°, pure blue 264°, indigo 276° and violet 292°.
- Water hue bands therefore use OKLab whenever the CSV has the OK columns:

| Band | OKLab hue |
|---|---|
| neutral | chroma below 0.02 |
| green | below 180 |
| cyan | 180 to 235 |
| blue | 235 to 270 |
| indigo | 270 to 282 |
| violet | 282 and above |

- The JSON key `violet(>=265)` is kept for compatibility. With OK columns it means OKLab 282 and above.

## Data sets

None of the data is in git.

| Set | Location | Notes |
|---|---|---|
| Market before/after pairs (m1-m6) | `DeveloperMedia/eval/market/{raw,ref}/` | Private. They were cut from web images the product owner shared. m5 (coral with a colour chart) and m6 (manta) are Sea-thru results, from a method that uses RAW images and measured distance. |
| Real photos (r01-r15) | listed in `real_set.txt`, relative to `DeveloperMedia/` | The product owner's own dive photos. No reference exists. r14 and r15 are the green or teal examples. |
| Neutral ramp | generated by `make_neutral_ramp.py` | A correct pipeline keeps it colourless. |
| AquaColorFix triplets (O1-O5, A1-A5, H1-H5) | `DeveloperMedia/eval/aquacolorfix/` | Private. `On` is the source, `An` the AquaColorFix output (a product-look target, not ground truth), `Hn` a UnderBlue iPhone export from 26 Sep 2026. See [the benchmark](../../docs/AquaColorFixBenchmark.md). |

- All developer media lives in `DeveloperMedia/` at the repo root. It is git-ignored and outside every Xcode target.
- Never put media under `UnderBlueTests/`. That folder is a synchronized Xcode group, so git-ignored files there are still copied into the test bundle.
- Same-named files in two folders break `build-for-testing`.

The UIEB set (890 pairs + 60 challenging) was removed on 2 Oct 2026. Its dev and holdout scores in older docs cannot be re-run.

## How to run

```sh
# Tuning scorecard on the current working-tree sources:
scripts/color-eval/tune_eval.sh my-run
# The same on another source folder, for example a copy of git HEAD:
HT_EVAL_SOURCES=/path/to/Processing scripts/color-eval/tune_eval.sh head-run
# AquaColorFix development gate (photo and video path, one line each):
scripts/color-eval/aquacolorfix_eval.sh my-run
# Score any five rendered files against A1-A5, for example an iPhone export set:
python3 scripts/color-eval/aquacolorfix_benchmark.py --underblue-files "/path/H{n}.jpg" --label phone
```

Environment variables:

| Variable | Default |
|---|---|
| `HT_EVAL_SOURCES` | `UnderBlue/Processing` |
| `HT_EVAL_DATA` | `DeveloperMedia` |
| `HT_EVAL_MARKET` | `DeveloperMedia/eval/market` |
| `HT_EVAL_OUT` | `$TMPDIR/underblue-color-eval` |
| `HT_EVAL_MAXDIM` | 640. The longest side of the render. The AquaColorFix gate uses 960. |
| `HT_EVAL_LOG` | unset. Set it to print every image's analysis, correction values, plan, and a probe of the water, neutral and mean colours through the colour kernel and the whole finishing chain. |
| `HT_EVAL_PNG` | Set to `1` to save lossless sRGB PNG companions alongside JPEG sheets. Use PNG for patch/noise measurements. |

- Results never go into the repo.
- The first run compiles the Core ML depth model into the cache.

The harness compiles a fixed list of Processing files (`common.sh`, `build_eval`). A new colour source file must be added to that list, or the build fails with a missing symbol.

`tune_eval.sh` prints `report.txt` and writes two sheets: `market_sheet.jpg` and `real_sheet.jpg`. Open the sheets and judge them by eye. The numbers do not show everything.

### Neutral surfaces

`tune_report.py` also measures three regions that should be colourless after correction. For each variant it takes the per-channel median in a fixed box, and reports its OKLab chroma (0 = colourless):

| Region | Box (share of the image: x0, y0, x1, y1) |
|---|---|
| m5 sand | 0.70, 0.88, 0.85, 0.98 |
| m5 colour chart, grey row | 0.618, 0.839, 0.663, 0.849 (approximate: the chart is small and tilted) |
| m6 manta belly | 0.44, 0.38, 0.56, 0.50 |

The boxes were placed by eye. Check them again if an image is replaced.

### m5 panel evaluation (native macOS)

```sh
# Native kernel/CPU and behavioural checks; no simulator:
scripts/color-eval/native_checks.sh
# Render at the source's 1600-pixel width and annotate 18 chart patch interiors:
scripts/color-eval/m5_eval.sh m5-candidate /path/to/baseline/render
# A source snapshot can produce the baseline with the same renderer:
HT_EVAL_SOURCES=/path/to/baseline/Processing scripts/color-eval/m5_eval.sh m5-baseline
```

The optional baseline directory must contain the same-size `m5__*.png` images. The report
includes per-patch CIE76 differences, whole-frame and water/coral/sand regions, black-pixel
share, and a local high-pass chroma proxy. On textured coral that proxy includes real texture;
use the flat water and sand regions to assess noise. `render/m5_regions.png` shows the masks,
`render/m5_comparison.png` shows original/baseline/candidate/reference, and
`render/m5_metrics.json` retains every measurement. A lower average does not certify acceptance:
patches that get worse by more than one CIE76 unit are explicitly listed. This one-unit reporting
threshold is not a perceptual acceptance threshold or a calibrated chart tolerance.

The chart is tilted and its bottom edge is obscured by sand. Interiors, not row-wide rectangles,
are sampled. Its reference grey row is visibly cyan; reference similarity and neutral correctness
are different measures. No chart colour/coordinate is available to production processing.
See [the implementation evaluation](../../docs/M5ColorEvaluation.md) for results and remaining gaps.

## Guards used for tuning

A change is accepted only if all of these hold:

- The neutral ramp's max Lab chroma is 3 or less, on both `combined` and `uniform`.
- Real photos: no image ends in indigo or violet (OKLab 270 or more) unless its original was already there. r04's anemone is really magenta.
- Keep what the market pairs gained so far.
- Neutral surfaces: chroma does not rise above the committed code, on both `combined` and `uniform`.
- AquaColorFix gate (pairs 2, 4 and 5): the mean ΔE does not rise above the committed code by more than 0.1. (A sharpening step moves texture pixels that are not aligned with AquaColorFix's, so any effective one costs 0.02 to 0.07.)
