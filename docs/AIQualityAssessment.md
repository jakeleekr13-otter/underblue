# AI 프리셋의 품질 평가(QA)와 보완 모델 설계

작성일: 2026-10-07
상태: **개발 보류.** 초기 복원 후보가 사용자 비교에서 체감 이득을 보이지 않아 QA/조건부 모델 학습으로 확대하지 않음. [파일럿 결과](AIRefinerPilot.md)

## 판단

1차 보정 결과를 평가하고 부족한 부분을 보완하는 방향은 타당하다. 다만 UIQM을 정답으로 취급하거나, 공개 IQA 모델이 곧바로 결함 지도를 준다고 가정하거나, 두 모델을 묶은 ONNX 파일이 Core AI에서 자동으로 빨라진다고 전제하면 안 된다.

기존 [개발 계획](AIPresetDevelopmentPlan.md)에 **오프라인 QA 기준 마련 → 복원 모델 단독 비교 → 필요한 경우 QA 조건부 모델 → 실기기 최적화** 순서를 추가한다. QA부터 검증하되, 첫 출시를 위해 무거운 평가 모델을 반드시 앱에 넣지는 않는다.

이 문서의 입력 B는 독립 AI 프리셋이 만드는 고정 기본 보정 결과다. Custom 설정이나 직전 프리셋 출력을 상속하는 기능으로 바꾸지 않는다.

## 제안에서 바로잡을 점

| 제안 내용 | 검토 결과 |
|---|---|
| UIQM이 수중 평가에 필수이며 색의 자연스러움을 보장 | 유용한 비교 지표지만 단독 합격 기준은 아님 |
| UICM/UISM/UIConM으로 결함 원인을 바로 진단 | 통계적 특징이며 의미 있는 원인 진단과 다름 |
| UIQM을 먼저 신경망으로 증류 | 우선 공식을 오프라인에서 계산. 비용이 실제 병목이고 목적이 명확할 때 증류 검토 |
| HyperIQA/MUSIQ가 점수와 해석 가능한 결함 맵을 반환 | 기본 공개 인터페이스는 그러한 계약이 아님. 결함별 출력은 별도 설계·라벨 필요 |
| NAFNet/Restormer에 QA feature_map을 바로 전달 | 공개 기본 모델은 이미지 입력. 조건부 입력을 받도록 수정·학습해야 함 |
| 두 모델을 한 클래스에 넣으면 동시에 실행되고 경량화 | 제안 코드에서는 QA 특징에 의존해 보완이 이어짐. 래핑만으로 연산 공유가 생기지 않음 |
| PyTorch → ONNX가 Core AI의 기본 변환 경로 | PyTorch/torch.export → coreai-torch → .aimodel이 확인된 공식 경로 |
| 반환 quality_score가 최종 이미지 품질 | 제안 코드에서는 보완 전 입력의 점수 |
| 수중 복원율 92% 표시 | 물리적 복원율 근거가 없으므로 사용하지 않음 |

## 1. UIQM은 보조 평가축으로 사용

UIQM은 색채(UICM), 선명도(UISM), 대비(UIConM) 관련 통계를 결합하는 비참조 지표다. [원 논문 저자 안내](https://www.karenpanetta.com/publications/journal-articles/human-visual-systems-inspired-underwater-image-quality-measures)

다음은 구분해야 한다.

- UICM이 높다고 피사체의 실제 색이 정확하거나 붉은색 과보정이 없다는 뜻은 아니다.
- UISM이 높다고 실제 정보가 복원됐다는 뜻은 아니다. 노이즈·강한 경계 강조도 선명도 통계에 영향을 줄 수 있다.
- 대비가 높아져도 암부나 하이라이트의 정보가 잘릴 수 있다.
- 이 세 값은 자동으로 물/산호/피부를 구분하거나 각 영역의 올바른 색을 알려주는 feature map이 아니다.

UIQM 등 수중 비참조 지표가 주관적 품질과 일치하지 않거나 붉은색 과보정을 제대로 벌점화하지 못하는 사례가 보고돼 있다. 따라서 UIQM 상승만으로 모델을 채택하지 않는다. [한계 분석 논문](https://arxiv.org/abs/2207.05470)

처음에는 다음을 같은 평가표에 남긴다.

| 축 | 기록할 내용 |
|---|---|
| UIQM 계열 | 전체값과 세 구성값, 구현 버전/색 순서/입력 범위/해상도/블록 설정 |
| 색 | 흰 피사체·모래와 물의 색 변화, 과채도·보라색/초록색 잔여, 색상표가 있으면 적합한 색 차이 |
| 노이즈·디테일 | 평탄한 물의 노이즈와 비늘·산호·기포의 보존을 분리 |
| 출력 결함 | 클리핑, halo, 검은 영역, 번짐, 타일 이음새 |
| 사람의 판단 | 이름을 가린 비교, 개선/동등/악화, 결함 이유 |

Python으로 먼저 기준 계산을 검증한다. 온디바이스에서 필요해졌을 때 Swift/Accelerate/Metal 또는 지원되는 텐서 연산으로 옮기는 선택지가 있다. OpenCV 코드가 일반적으로 자동 ONNX 내보내기를 제공한다고 가정하지 않는다.

UIQM 증류 모델은 그 지표를 근사할 뿐 지표의 한계를 해결하지 않는다. 구현 간 수치 차이와 근사 오차까지 생기므로 현재의 우선 작업은 아니다.

## 2. 학습형 QA는 별도 라벨과 검증이 필요

[HyperIQA 공식 데모](https://github.com/SSL92/hyperIQA/blob/master/demo.py)는 패치별 예측을 합쳐 점수를 만든다. HyperNet의 내부 반환값은 TargetNet의 가중치·입력 특징이며, 기본적으로 붉은색 부족/노이즈 심함 등의 설명 가능한 결함 지도를 주는 것이 아니다. [모델 정의](https://github.com/SSL92/hyperIQA/blob/master/models.py)

[MUSIQ 공식 구현](https://github.com/google-research/google-research/tree/master/musiq)은 JAX/Flax 기반이며 TensorFlow 전처리를 사용한다. 공개 체크포인트는 학습 데이터와 목적에 따라 점수 또는 점수 분포를 예측한다. PyTorch 예제 클래스에 그대로 끼울 수 있는 동일 인터페이스가 아니다. [추론 코드](https://github.com/google-research/google-research/blob/master/musiq/run_predict_image.py)

잠재 특징을 추출할 수 있다는 것과 그 특징이 노이즈·적색 부족의 원인을 나타낸다는 것은 다르다. 설명 가능한 QA가 필요하면 다음과 같은 라벨을 별도로 정의한다.

- 전체 선호도 또는 쌍별 선호.
- 색의 부자연스러움, 노이즈, 흐림, 클리핑, halo, 디테일 소실 등 결함 종류와 정도.
- 필요한 경우 영역별 라벨 및 불확실성.
- 평가자 간 일치도와 판단 불가능 사례.

수중 보정 결과를 학습에 추가했다는 사실만으로 0~100 점수가 교정되지는 않는다. 장면별 독립 확인 자료에서 사람 평가와의 순위 일치·점수 보정·결함 검출 오차를 확인해야 한다.

### UIEB 사용 조건

UIEB 공식 구성은 원본/참고 보정 이미지 890쌍과 어려운 사례 60장이다. 원본·참고 보정 이미지 쌍 자체가 각각의 품질 점수 85점이나 픽셀별 결함 정답을 제공하는 것은 아니다.

공식 페이지는 **비상업용·학술용**, 재배포 금지를 명시한다. 현재의 유료 AI 애드온 개발에 허용된 학습/배포 자료라고 간주하지 않는다. 별도 허가 범위를 확인하거나 상업적 사용 조건이 확인된 자료 및 사용 권한이 있는 직접 촬영 사진으로 계획한다. [UIEB 공식 페이지](https://li-chongyi.github.io/proj_benchmark.html)

주관적 점수 자료의 예로 UID2021은 사람의 평가(MOS)를 포함한다. 다만 연구용 공개 안내를 상업용 허가로 해석하지 않으며, 자동 대체 학습 데이터로 선정하지 않는다. [UID2021 논문](https://arxiv.org/abs/2204.08813)

현재 평가용으로 보유한 외부 이미지도 파일이 로컬에 있다는 이유로 학습·재배포 권한을 얻는 것은 아니다. 평가 자료와 제품 학습 자료의 출처/사용 범위를 별도로 기록한다.

## 3. 복원 모델과 조건부 입력

[NAFNet](https://github.com/megvii-research/NAFNet/blob/main/basicsr/models/archs/NAFNet_arch.py)과 [Restormer](https://github.com/swz30/Restormer/blob/main/basicsr/models/archs/restormer_arch.py)의 일반 복원 경로는 입력에 잔차를 더해 완성 이미지를 반환한다. 기본 호출은 이미지 하나를 받으며, QA 특징을 두 번째 인수로 받는 구조는 아니다.

두 모델은 2022년 연구이며, 고해상도 복원 효율이 곧 작은 모바일 모델이나 iPhone 성능 검증을 뜻하지 않는다. NAFNet의 작은 후보를 먼저 비교하고 Restormer는 품질 비교 후보로 둔다. 각 노이즈 제거/흔들림 제거 체크포인트의 목적도 구분한다.

조건부 보완을 도입하려면 다음을 새로 설계해야 한다.

- QA 특징의 형태·크기·의미와 이미지 좌표 정렬.
- 보완 모델에 특징을 전달하는 방식(채널 결합·조건부 정규화 등의 후보).
- 조건부 모델을 위한 학습 자료와 손실.
- QA 오류가 보완을 악화시키는 경우의 완화와 실패 처리.

우선 동일한 입력과 평가 자료에서 **복원 모델 단독**과 **QA 조건부 복원**을 비교한다. 조건부 모델이 실제로 나아지고 기기 비용도 감당할 때 도입한다.

## 4. 제시된 예제 코드의 점수 의미

사용자 예제의 순서는 다음과 같다.

~~~text
quality_score, feature_map = QA(B)
F = Refinement(B, feature_map)
return F, quality_score
~~~

따라서 quality_score는 B의 점수다. F의 최종 품질이나 개선량이 아니다. 이름도 quality_before로 구분해야 한다.

개발 중에는 B와 F를 같은 **고정된 독립 평가 체계**로 각각 평가해 차이를 기록한다. 보완 모델이 자기 점수를 높게 내는 것만으로 품질을 인증하지 않는다. QA를 학습 손실로 사용하더라도 별도의 사람 평가와 확인 자료를 유지한다.

앱에서 두 번 평가하는 비용은 별도로 측정한다. 개발용 QA를 그대로 매번 사용자 기기에서 실행할 필요는 없다.

## 5. 한 모델 파일과 실제 연산량은 다름

두 네트워크를 nn.Module로 감싼다고 파라미터나 특징 추출 연산이 자동 공유되지는 않는다. 특히 예제는 QA feature_map이 나온 다음 보완 모델이 사용하므로 두 작업이 독립적으로 동시에 끝나는 구조가 아니다.

공유 인코더와 QA/복원 출력 헤드를 갖는 모델은 후속 후보가 될 수 있다. 하지만 새 구조와 학습이 필요하며, 멀티태스크 손실이 복원 품질에 미치는 영향까지 확인해야 한다. 품질 출력이 실제 실행에 필요 없다면 학습용 보조 헤드만 두고 배포 시 제거하는 방식도 비교할 수 있다.

단일 파일, 단일 호출, 다중 출력만으로 속도 개선을 주장하지 않는다. 전체 지연·메모리·기기 연산 지원을 측정한다.

## 6. Apple 변환 경로

현재 프로젝트에서 확인한 경로:

~~~text
PyTorch 모델
→ torch.export
→ coreai-torch / TorchConverter
→ .aimodel
→ iOS 27+ AIModel / InferenceFunction
~~~

[Apple 공식 통합 안내](https://developer.apple.com/documentation/coreai/integrating-on-device-ai-models-in-your-app-with-core-ai)

ONNX는 다른 실행 환경과의 호환 목적일 때 별도로 검토할 수 있지만, Core AI의 필수 중간 산출물이나 기본 실행 모델로 계획하지 않는다. 예제의 torch.onnx.export 실행만으로 iOS Core AI에서 바로 사용할 모델이 생기지는 않는다.

여러 출력은 사용할 수 있으나 입출력 계약과 연산 지원을 검증해야 한다. 이전 실험의 FP32 중간값/Neural Engine fallback 문제도 새 그래프에서 다시 확인한다.

## 7. 앱 점수 표시

초기 제품에서는 수중 복원율 92%와 같은 표현을 사용하지 않는다. 비참조 품질 점수는 실제 손실 정보 중 몇 퍼센트가 복원됐는지를 측정하지 않는다.

- 개발 중: 원시 지표와 결함 기록을 내부 도구에서 사용.
- 사용자 화면: AI 준비/완료, 전후 비교, 사용자가 정한 강도를 우선 제공.
- 보정 품질 점수: 수중 자료에서 충분히 교정·검증한 뒤 별도로 검토. 기준과 불확실성을 설명할 수 있어야 함.
- 결함 문구: 해당 결함을 실제로 검출하도록 학습·검증하지 않았다면 표시하지 않음.

원본 비교와 AI 전후 비교도 구분한다. 점수 표시 때문에 독립 AI 프리셋의 기존 흐름을 바꾸거나 일반 프리셋에서 추가 AI를 실행하지 않는다.

## 8. 반영한 개발 순서

1. 권한이 확인된 사진과 고정 기본 보정 B를 준비한다.
2. 오프라인 QA 표에 UIQM 구성값·기존 색/노이즈 지표·사람 평가를 함께 남긴다.
3. 공개 복원 모델 단독으로 B→F의 실제 이득을 검증한다.
4. 평가 지표와 사람 판단의 불일치를 분석한다. 필요한 경우에만 학습형 QA와 결함 라벨 작업을 추가한다.
5. QA 조건부 모델과 단독 모델을 비교한다.
6. 유망한 구조를 .aimodel로 변환하고 FP16·타일·압축·실기기 성능을 검증한다.
7. 확인된 효과와 비용에 맞춰 독립 AI 프리셋에 연결한다.

UIQM 구현·QA 점수 학습·조건부 모델은 진행하지 않았다. 초기 복원 모델 단계에서 품질 조건을 통과하지 못해 이 확장을 보류한다.
